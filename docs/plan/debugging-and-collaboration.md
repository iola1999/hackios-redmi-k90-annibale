# HackiOS 项目排查与协作手册

本文记录 REDMI K90（SM8750，`annibale`）移植中可复用的排查方法、判断依据、存储安全和协作约束，回答三个问题：下一步检查什么、这个检查能区分哪些原因、结果支持多大范围的结论。更新日期 2026-11-05。

当前命令见[真机调试手册](device-test-playbook.md)，真机轮的计数口径、收尾和重试见[真机轮运行规则](k90auto-run-protocol.md)，阶段安排见[总账](2026-10-23-tracking.md)，案例见[桌面交互案例](../analysis/2026-10-24-interactive-runtime.md)和[A830 命令执行案例](../analysis/2026-10-24-a830-command-startup.md)。

## 1. 先定义问题和完成条件

- 接手先读用户最近的完整反馈，确认目标、已授权操作、数据保护要求和已尝试的恢复动作。摘要只用于定位，重要判断回到实际命令、输出和源码；设备状态、构建输出和未提交修改都可能已被其他会话改变。
- 把现象转换成可检查的状态：「没有通知栏」对应 SystemUI 进程、窗口和崩溃记录，「手机没反应」要区分 USB 枚举、协议响应、内核运行和面板显示。
- 完成条件直接对应目标：编译成功验证构建，上传成功验证传输，SpringBoard 进程、framebuffer 与用户实际操作共同验证界面。某层通过后继续验收依赖它的下一层。
- 用户的视频、截图和反馈先关联到具体一轮，确认是否最新、是否加载壁纸、实际 renderer。合成触摸只验证界面流程，物理按键还要查驱动初始化与真实按压。改了启动配置，把此前可用的按键、电量和触摸列入回归项。

## 2. 用能区分原因的实验推进

- 每轮先写出竞争解释和各自的预测，选能让不同原因产生不同结果的检查。「没有内核日志」可能来自内核未执行、输出分支未采集、缓冲被替换或主机读取失败，重启区分不了，检查写入点与缓冲状态能区分一部分。
- 多项检查都能区分时，选副作用少、范围明确、失败后可恢复的一项；读已有状态能回答的先读状态。判据依赖「某机制会留下痕迹」，先读源码验证前提：`/private/var` 在本移植里是 ramfs，读路径不更新 `rn_atime`，用 `st_atimespec` 判断文件是否被读过不成立。
- 一次只改一个影响执行的条件，冷启动与复用继承状态也算条件。改了多个条件后成功只确认该组合可用。修正一处差异后，分别记「差异已修正」和「原故障是否改变」；结果没变，先确认修改进了运行产物。
- 分段计时决定先改哪里。新建 GPU 缓冲慢，分配和等锁只占少部分，继续拆到 GPU 映射的地址查找和页表发布，缩小处理范围后耗时下降。
- 画面错误要辨认错误内容的来源：蓝色色块里出现了本应在屏幕上方的电池图标，调查转向分块之间的数据复用，最后找到 framebuffer fetch 读旧内容前缺一层缓存失效。
- 对照成立前检查输入与触发场景：关闭纹理压缩的一轮没有闪烁，但 GPU 初始化提前失败、回退到软件绘制，原场景没有运行。未复现只覆盖所测时长与场景。
- 故障总在某项操作附近出现，先暂不执行该操作，在覆盖原故障窗口的时间内观察，区分经过时间与新增调用的影响。
- 关键配置未知时，先找所有候选共同支持、有来源的条件，限定实验范围和退出方式。参考表来自其他板型，要用本机设备树重核 revision、SKU 和工作点（参考表的 125 MHz 本机没有）。
- 最后一条日志只确认该输出已执行，可疑调用前后的成对标记能划分范围。异步系统的生效时刻单独确认：发布队列索引后对方可能已经读取命令。
- 能提取的解析、计算或内存操作先写主机测试，预期来自独立的格式定义和真实输入，配置取自生产声明；删除保护分支后测试必须失败。协议测试覆盖错误后的下一步，例如「预期失败 → 下一条查询成功 → 后续上传成功」。
- 性能指标对应用户动作：一次手势分别测首帧等待、动画内帧间隔与长帧，整轮平均会混入静止期。采样到的用户 PC 受进入内核的时机影响，分布不能直接换算成时间占比。一处耗时缩短后重测剩余部分，收益不足就保留原配置。

## 3. 沿实际使用的数据追踪源码与产物

| 状态 | 为什么需要单独确认 |
|---|---|
| 顶层仓库与两个 submodule | 父仓只记录子模块 commit |
| `hackios-xnu-kernel` 与 `.userland.git` | 共用工作目录；驱动、shim 与 `tools/mesa/` 用 `common/ugit add -f <路径>` 提交，`hackios-xnu-userland` 的提交从这里移植 |
| 12377 内核构建树 `out/xnu12377-cmd`（更早的一棵是 `out/xnu12377`） | 独立 git 目录（分支 `redwood26`），顶层 `git log --all` 查不到它的提交；改动从 `xnu/files/` 复制进去，见 [k90auto 说明](../../tools/k90auto/README.md) |
| `xnu/files/`、`xnu26/patches/` 与展开树 | 仓库来源和实际编译输入可能不同，没有双向同步 |
| 宿主与 `kbuild` 的 `/work/repo` | 容器用持久卷 checkout，宿主更新后要同步 |
| 编译结果、打包输入与设备 RAM | 还要核对选择、打包、上传和本轮实际使用 |

- 按「源码 → 展开树 → 编译结果 → payload → 设备日志」追踪实际输入，记路径、SHA-256、启动参数和版本，不靠文件名。启动参数也是输入：按键和电量缺失曾对应 cmdline 漏了 `buttons=1 battery=1`。
- 生成器的计数与实际输出分别检查（循环变量复用曾让按需服务缺了 PosterBoard 配置）。「改了」都要从产物读回来验证，实例见[运行规则 §3](k90auto-run-protocol.md#3-改了但没生效)。
- 内核镜像说明不了自己的源码：版本串里的 `aec10a9` 是移植线基提交，不同内核可以逐字相同；构建树带着未跟踪的移植源码（`bsd/dev/adreno8*.c` 等），`xnu26/apply.sh` 在目录已存在时直接退出。一轮跑的是哪个内核，以 `kernel.json` 和轮次 manifest 的内核哈希为准。镜像嵌入源文件绝对路径（`__FILE__`），发布前要检查。
- 产物哈希只能单向用：相同可以推出源相同，不同推不出源不同。`hackios-xnu-kernel/tools/mk-mesa.sh` 开头注释记录了容器 theos 线同源两次构建字节大量不同。
- 跨模块配置按生产者、格式、消费者逐段核对单位、长度、对齐、字节序和执行分支，分配页与设备映射页、字节与协议字数分别定义。布局或起点变化后重查内存前提：队列开始跨页，只覆盖单页的 CPU 映射就不够。
- 资料冲突先核对适用的芯片、板型、版本和执行路径；revision、驱动 catalog 和固件文件名分别确认，文件名相同仍核对二进制版本。公开源码解释不了本机行为，先提一个具体问题，再按符号定向看实际加载的二进制。
- 逆向用宿主机的 idalib MCP：大文件 `idb_open` 传 `run_auto_analysis: false`，只查具体地址；`idb_close` 的 `save` 传 false，否则会在被分析文件旁写 `.i64`。`QuartzCore`、`CoreAnimation`、`Metal` 等库在 `ios26/rootfs` 下没有磁盘 Mach-O，代码只在共享缓存 `hackios-xnu-kernel/ios26/23G90__iPhone18,3/`（85 个文件、4.9 GB）里，见 [26 虚表定位](../analysis/2026-10-29-quartzcore-vtable-26.md)。
- 比较初始化顺序要追踪资源申请、框架回调和首次启动的完整调用关系。同一驱动有多种模式时先确认本机走哪个入口：普通 HFI 与硬件调度模式的 START 顺序不同。等待应答期间对方发来的资源请求必须处理或明确失败。
- 接口是否存在按编译或运行结果、代码实际用法、头文件的顺序采信，并写明是哪棵树：`xnu12377` 的 `ctl_bind` 在 `<sys/kern_control_private.h>` 的 `KERNEL_PRIVATE` 段里。
- 容器不可用时，从构建树 `BUILD/obj/DEVELOPMENT_ARM64_BCM2837/compile_commands.json` 取同类文件的 `arguments` 编单个文件，再用 `nm -u` 对照 `mach.development.bcm2837.unstripped`，能确认编译与符号可见性。
- `xnu26/build-macos.sh` 增量构建有三条约束：`*/conf/Makefile.template` 含 `${OBJS}: $(firstword $(MAKEFILE_LIST))`，修改 `*/conf/files` 触发 `doconf` 重写 `Makefile` 后会让该子系统全部 `.o`／`.cpo` 全量重编，把 `Makefile` 时间戳改回早于 `BUILD/obj/SETUP/config` 又会让 `gmake` 重跑所有子系统的 `doconf`；`makedefs/MakeInc.cmd` 已对子 make 传 `MAKEJOBS=--jobs=$(hw.ncpu)`，外层再传 `-jN` 会重置 jobserver 并成倍派生编译进程；Xcode clang 21 在 `-Weverything` 下会对内核头文件双下划线宏输出数百 MB 的 `-Wreserved-identifier` 诊断。`xnu26/build-macos.sh` 已自动剔除外层 `-j` 并将 `DOCONFDEPS` 与生成 `Makefile` 的时间戳钳制在 `SETUP/config` 与存量 `.o` 之间，`xnu26/xcrun` 已对 `clang`／`clang++` 追加 `-Wno-reserved-identifier -Wno-reserved-macro-identifier`。
- 容器内执行后检查文件和 diff 再构建：heredoc 经 stdin 传入要 `docker exec -i`，漏掉时曾退出 0 而文件未改。复制、打包、上传按依赖检查前一步结果；跨环境复制根目录保留目标系统的符号链接语义。
- 构建命令见[内核构建说明](../analysis/kernel-build-linux.md)，arm64e 用户态产物见 [arm64e 构建路径](../analysis/2026-10-28-arm64e-userland-build-path.md)。

## 4. 把日志和诊断代码纳入被检查对象

- 日志有自己的执行路径：产生函数、console 选择、缓冲写入、loader 读取、主机保存；`kprintf`、`printf`、`IOLog` 与 `/dev/console` 可能走不同分支。日志为空先查输出分支和缓冲状态。
- 用「没有错误」排除原因前，确认检查已执行、覆盖失败阶段并在复位前取得结果。GMU 失败日志起初缺 SMMU 故障检查，补读后才发现故障。
- 没有报错的停滞先找具体的等待条件，再查负责完成它的模块：A830 两个执行单元停在同步等待，第三个单元的独立访存标识缺了路由。
- 异常报告路径少依赖出错子系统：持有 console 锁时再打印会锁重入（曾定位到 `_vcputc_lock`）。先保存错误正文、PC、LR、ESR 和 FAR。
- 诊断会占用时间、改变调度和锁行为并访问硬件，临时提前返回和高频日志只覆盖诊断配置，定位后清理或留开关。减少检查次数前写明最多允许多晚发现故障。
- 周期采样配合区间峰值和状态转换计数；频率请求、协议应答、软件档位和实际时钟分别报告。统计脚本先用已知日志核对字段与单位，零个异常只在有效样本存在时有意义。
- 地址分析用本轮实际运行的二进制。短暂故障在运行期间保存快照并记主机单调时间，一次请求超时只说明该请求未在限时内完成。`sort -u` 后是文本序，带时间语义的序列按 `tl:` 等锚点重建时间轴。
- 一行日志先读产生它的代码再推断含义：`NOT_RUNNING hung-held` 只在 `getvar result` 不为 `running` 时打印，`hung-held` 是 loader 那一刻的应答，据字面推断「起轮时设备停在 hung-held」是错的。转述别人的结论时标明推断部分。
- 枚举类命令输出不截断：`adb devices | tail -2` 会漏掉第二台设备。搜索遵守 `AGENTS.md` §6 的检索约束，实测见[运行规则 §4](k90auto-run-protocol.md#4-轮次目录与固定收尾)。

## 5. 用状态和资源归属理解设备行为

Android、LK fastboot、fastbootd、驻留 loader 和 XNU 是不同的执行环境，切换后重新枚举并查询身份；Android／LK 的序列号由 `ANDROID_SERIAL` 提供，loader 是 `xnuloader`。loader 与 XNU 在不同 CPU 上并行运行，共享中断控制器、定时器、内存和固件资源。

### 硬件身份与寄存器来源分别核对

- 设备身份、寄存器地址、位域和访问权限各要独立来源，常量重复出现可能来自同一个假设。
- MMIO 需要有效映射、地址、宽度、电源及权限；诊断打印和平台识别也会访问寄存器，旧平台识别曾因此阻断启动。未知身份不能继续执行机型专属写入。
- 源码缺某项设置，先读接管后的实际状态：新增总线时钟使能前该位已置位，实验只确认了继承状态。字段位宽与总线访问宽度分别检查，基址、偏移和步长写出完整计算。
- 权限按访问主体、特权级、读写或取指与页属性组合判断：允许非特权写入的页禁止特权取指，清除对应 AP 位后 GMU 才启动。
- 回读不一致先分类（控制位、可选提示、固定读值、保留位），命令寄存器可能写入后自清。
- 映射越界按实际通道算完整地址：SPMI 整段映射后分配失败，最终按通道分别映射。软件页表从实际 TTBR 根遍历每页。
- 只读查询也查共享状态：设备树遍历的共享游标曾导致多线程 panic。配置回读、启用转换和设备实际访问分别验收。
- CPU 拓扑字段沿生成器、loader、内核 CPU 查找、secondary 入口和跨核心中断逐处检查，保留 Aff2 后两颗高性能核心才在线。
- 主机端检查退出码、stdout、stderr 和预期字段：fastboot 曾以退出码 0 输出 `FAILED`。macOS 没有 `timeout` 命令，用 Python `subprocess.run(..., timeout=...)`。

### 缓冲和镜像都有生命周期

- `oem log`、`oem screenshot` 准备数据，`get_staged` 读最近一次准备的内容，要成对、串行执行。内核正常返回后先取 `result` 再读已合并日志，额外调 `oem log` 会重新生成内容。
- RAM 系统盘在同一 loader 生命周期内可复用，整机重启后重新上传或从 DSU 读入。系统盘是 `md0`，`root.apfs` 是 `md1` 并挂到 `/redwood`，见[根文件系统说明](../analysis/rootfs-strategy.md)。
- 主机超时后设备端 USB DMA 请求可能还没结束，只有匹配的终止通知才能解除缓冲归属，见 [USB 恢复经验](../analysis/2026-10-25-usb-recovery-lessons.md)。
- 电源票值先分清是本方请求、聚合状态还是实际供给（ARC 读数只描述 DRV2 的请求）；读完只清理本轮新增的控制位。

### 恢复能力也是完成条件

- 实验前准备下一版产物、日志接收和恢复入口；失败先保存可用信息。
- 初始化只恢复本轮修改的部分。释放设备可访问的内存前，必须确认访问已阻止、映射已关闭、同步已完成，确认不了就保留内存。提交失败没返回 fence、解除映射或 TLB 同步失败时，相关内存和页表继续保留。
- 有副作用的固件请求可能先执行后应答，发送前就记「请求可能已生效」。EOP、核心空闲与 GMU 更新读指针可能先后可见，对未完成的一项加有界等待。
- 早期停滞可能处理不了 `oem stop`；重启命令的成功应答只说明进入了相应分支，要等重新枚举并查询新状态。
- 意外进入 Android，先查 LK 的槽位成功、可启动和重试计数：连续未标记成功的启动会耗尽 A 槽重试并回退到 B 槽，恢复见[引导目标切换 SOP](device-boot-target-sop.md)。
- 软件恢复不可用再请求用户按键，一次说明完整动作、预期画面和后续操作。真机轮中途失联的处理见[运行规则 §8](k90auto-run-protocol.md#8-失败与重试)。

## 6. 存储安全取决于所有权和时间

- `boot_a` 用于实验，B 槽保留 Android，两槽共用 userdata。原始块写入绕过文件系统分配，剩余容量、尾部全零或 Android 能开机都不能确认某段空间可写；写入前核对区段所有权、逻辑块大小、起始偏移和长度。
- 备份只覆盖采集时刻和指定范围：既有分区备份不含 `super`、`userdata`。备份数据说明在本地的 `annibale-backup/`。
- 系统盘经 USB 传入 RAM，或由 loader 从 Android DSU 读入（见 [README](../../README.md)）。`oem logwrite` 在缺少日志分区时会覆盖 `boot_a` 开头，诊断入口与常规读操作分别审阅。

## 7. 各子系统复用同一套判断方法

| 方向 | 优先区分的层次 | 验收边界 |
|---|---|---|
| Android 界面 | 进程 → 新崩溃栈 → 实际加载的包或插件 → 窗口 | 持续运行、新崩溃和用户操作 |
| 显示与触摸 | framebuffer 地址、宽高、stride、格式 → 内存内容 → 面板扫描；原始触摸 → 坐标变换 → iOS 注入 | 主机截图确认内存内容；物理画面和手势分别验收 |
| GPU | 固件 → 电源与时钟 → 地址映射 → GMU/HFI → 提交和 fence → Metal／UI | 软件 renderer 和真实 GPU 执行分别验证 |
| Wi-Fi | PCIe link/BAR → DMA/MSI → MHI → 固件/QMI → 数据传输 | 区分热启动继承状态与冷启动初始化 |
| 相机与音频 | 身份、时钟、电源、路由 → 缓冲与传输 → 帧或录放结果 | 格式、stride、长度及实际内容；播放与录音分别确认 |
| 按键、电池、振动、手电 | 原始读数与有效位 → 单项行为 → 退出状态 | 保留 fault、时长、限流及资源恢复条件 |

- 源码里有驱动或固件只确认实现存在；构建、最终镜像、设备初始化和用户可用行为分别验收，进度见总账和[路线图](2026-10-26-roadmap.md)。
- 总线通信成功后检查固件工作模式：身份稳定而事件全零，先核对报告开关、地址和格式（Goodix 要关闭 THP 原始帧、开启坐标上报）。电量、外部电源和充电状态需要各自的数据来源。
- 原有功能再次失败，先看本轮进程与最新错误；沿用旧修复前，先确认它针对的前提这次也成立。
- 借鉴其他项目时，编译通过、提交成功、fence 完成和结果正确分别统计。升级时按具体构建检查架构（同一系统版本可能分别提供 arm64 与 arm64e），先用最小程序验证加载和设备枚举；服务端对未知请求返回成功，客户端就会选择未实现的功能。

## 8. 与用户和其他会话协作

- 目标有缺口，先问一个会改变架构、数据模型或用户体验的问题，只读调查继续；视觉或交互先给低成本原型。
- 搜索从已知目录开始，用户明确反对无目的的全盘扫描。
- 沿用已有授权，新增影响先说明。工作更新说明新发现、剩余未知和下一步检查的作用。用户的画面、声音、触感和按键反馈是独立观察，用户修正观察后更新同一条结论。
- 用户质疑某个改动能否解决问题，先测量它对应的执行阶段，再解释收益范围。
- 用户暂时不能操作设备，优先跑能自行结束、保存结果并返回已知状态的一轮；光亮、震感和真实按压仍要人观察。

用户定下的长期规则：

- 性能按日用标准：验收口径是「不受热限制时 ≥60 fps」，附从冷机开始维持满频的时长，目标接近同一台手机上 Android 的表现。允许推翻现方案、大幅重构；先有可复现的持续重绘测量再优化。
- 改系统镜像是最后手段：先改本项目的 payload（`package.py` 的 job 清单、`JOB_USERS`、`var.skel`、shim 与 AIR 库），再改内核与启动参数，最后才改 iOS 系统镜像。改镜像前在 `docs/` 写下改动清单（路径、原因、有无原生替代、去掉后能否正常启动），一次只改一处。
- 需要人感知的外设（振动、亮度、声音、触感）先完成实现和无人值守能验证的部分，需要感知的项目列成清单，等用户在场时逐项确认；实现不等确认。
- 温度安全优先：测试不触发九十多度的温度，宁可功能验证不完整也不继续升温。
- 调频策略由操作系统决定；采用自建策略前说明已检查的路径和原因，并保留替换条件。

会话与任务之间：

- 同一设备只由一个任务发命令；共享构建树、overlay 和文档分别确认修改归属。长队列固定运行脚本及分析器版本，新脚本在独立副本准备。
- 派出子任务时写清实际输入、最后通过的步骤、首个失败动作、允许改的文件和交付要求；交付包含源码位置、实际修改、验证范围和未确认项。整合时统一选定文件版本、构建和上机，再查跨模块的单位、布局和生命周期。
- 历史总账与当前脚本冲突，先核对时间和实际行为。前提被推翻时，建立在它上面的建议一并撤回，并逐处点名已按它写下的产物。
- 重写远端可达历史（force push、删除远端分支或标签、改写已推送的提交）前停下等用户确认，说明将覆盖什么、内容保全怎么验证、误覆盖后的恢复路径。

## 9. 怎样维护这份知识

- 优先保留可复用的因果解释、判断顺序、数据边界和协作要求，整理方式见[经验整理 Prompt](experience-review-prompt.md)。新条目至少回答一个问题：它会改变下一轮的检查顺序、操作边界或验收标准吗？
- 每条保留一项最短的具体观察，写清原来怎样判断、哪条输出改变了方向、为什么选下一项检查。完整参数和逐轮输出放专题文档，同一方法的新案例补进原条目。
- 实现修改前追踪实际调用方和消费方；用删除该设计的思想实验检查必要性，跨模块修改按 `reclaim-code-entropy` 审查，拆文件遵守 `AGENTS.md` 的代码行数约定。
- 文档按 `AGENTS.md` §1 分类存放。原始日志和截图放在已忽略的 `docs/analysis/local/` 或 `docs/progress/evidence/`；写结论前用 `git check-ignore -v <目标路径>` 确认目标没被忽略。
- 交接保留当前目标、最后成功与首次失败的阶段、用户最新反馈、实际输入、未提交修改归属和恢复入口。提交前核对逐文件 diff、父仓及子模块状态。
- 读来源会话：dsh 数据在用户主目录的 `.dsh/sessions/`，用 `turnOutline` 定位后读对应的 `session.v4.jsonl.zstd`；Claude Code 的用户追加要求可能在队列事件或附件里。压缩摘要只用于导航。
