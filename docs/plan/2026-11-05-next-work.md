# 后续工作（2026-11-05 用户确认）

用户在 2026-11-05 看过当天的汇报后确认了下面五项的方向，要求先记成待办，暂不改动。每项写用户的要求、现状和下一步，调研细节在各项链接的文档里。

## 1. 蓝牙

- 要求：支持蓝牙。
- 现状：没有开始。WCN7850 的蓝牙走 SE14 UART，电源轨已由 Wi-Fi 代码打开；`bluetoothd` 不在系统盘上，见[蓝牙接入调研](../analysis/2026-11-02-bluetooth-bringup.md)。
- 系统盘：`bluetoothd` 有 12 MB，超过选取规则的 10 MB 上限，按用户要求放进系统盘。重做系统盘后 DSU 里那份也要更新，§2 的写入路径做好之后可以只写变化的部分。
- 下一步：按调研 §6 的顺序，先跑一轮只起芯片（UART 驱动与固件下载），再接 iOS（Skywalk 通道、BlueTool 替身、`bluetoothd` 任务与环境变量）。

## 2. 跨开机保留数据

- 要求：设置、加入过的 Wi-Fi、装上的应用在重启后保留。
- 结论：DSU 系统盘槽位的尾部可以写，dada 的 loader 已在同一种 DSU 文件里原地写入；对 Android 的影响与风险见[跨开机保留数据的可行性](../analysis/2026-11-05-persistence-feasibility.md) §6。
- 下一步：按可行性文档 §5 推进，第一步只读，loader 打印槽位尾部的扩展区并确认内容全零；写路径要带范围检查、头部哈希核对和回读，再接 `var_store` 的保存与开机展开。
- 首次写入之后在 Android 里核对 `gsi_tool status`、开机与用户数据正常。

## 3. 亮度

- 要求：亮度由系统里的亮度设置（控制中心与「设置」的滑块）控制，调的是面板背光，默认打开，不用开机参数。
- 现状：内核 `6027b2d` 发布了 `AppleARMBacklight`，iOS 经 `IOMFBBrightnessLevel` 把尼特数发到内核；面板背光仍是开机时 loader 设定的亮度，`fb_dim=1` 时只调暗画面，见[屏幕亮度调节调研](../analysis/2026-11-02-brightness-control.md) §9。
- 下一步：按调研 §7 的第 3、4 步，经 DSI 给面板发 DCS `0x51`，先在开关后面发一次固定值、由人确认亮度变化，再把 iOS 的尼特数换算成面板亮度值（上限暂取出厂的 0x1a5e）。面板调光可用后默认打开，混合器调暗是否保留到那时再定。
- 风险：发错的命令可能让面板卡住，只能重启手机恢复。
- 重启后保持上次的亮度依赖 §2。

## 4. GPU 性能（记录问题）

- 问题：120 Hz 屏上控制中心下拉约 90 帧／秒、翻页 90～100 帧／秒，长帧以 GPU 时间为主；一帧里 backboardd 提交 4 次以上时，七成以上是长帧（`rate8-ns1`），读数见 [11-05 记录](../progress/2026-11-05-defaults-and-charging.md) §3.1。
- 已有分析：[120 Hz 手势瓶颈](../analysis/2026-11-01-120hz-gesture-bottleneck.md)、[GPU 升频之后的长帧](../analysis/2026-11-02-120hz-after-gpu-clock.md)，候选做法列在[上游对照](../analysis/2026-11-05-upstream-lessons.md)。
- 暂不处理。亮度服务默认打开前，要先比一次它对手势帧率的影响。

## 5. 视频硬件解码（记录问题，调研方案）

- 问题：Safari 里 H.264 视频报 `err=3:Media failed to decode`，VP9 停在 `loadedmetadata`，读数见 [11-05 记录](../progress/2026-11-05-defaults-and-charging.md) §3.5。
- 原因（调研结论，未上机验证）：H.264 由系统自带的软件解码器 H264SW 解出画面，backboardd 里我们的 Metal 驱动拒绝合成两平面 YCbCr（`'420v'`）画面，推断这是黑屏和报错的直接原因；VP9 没有可用的解码器，WebKit 自带的 VP9 软件解码只在内部开关 `SWVPDecodersAlwaysEnabled` 打开时注册。
- 硬件解码：SM8750 的视频块是 Iris VPU v3.5，主线 Linux 已支持，工作量以周到月计。要做的三件事：
  - 从 Android 的 odm 或 vendor 分区只读取出厂商签名的 vpu35 固件。
  - 内核驱动：上电、经 PAS 加载固件、配 SMMU、起 HFI gen2。
  - VideoToolbox 解码插件，注入 videocodecd 与 WebKit 的 GPU 进程。
- 建议顺序：先跑一轮诊断（支持 Range 的测试页服务器、播放进程的日志、`vt_test` 测软件解码速度），再做两平面 YCbCr 合成。这一步是软件解码和硬件解码共同的前提。之后调软件解码线程数、在 MobileSafari 里打开 VP9 软件解码，最后做 Iris 硬件解码。
- 调研全文见[视频解码调研](../analysis/2026-11-05-video-decode.md)，建议顺序在 §6。
