# 性能、画面与基本功能故障排查 SOP

从用户能重复的动作开始，找到输出第一次出错的位置，再用同一动作验收。下文的主机命令从仓库根目录执行。`round` 和 `baseline` 分别指向两次已结束的轮次目录，形如 `docs/progress/evidence/k90auto/kernel-<NAME>-<LABEL>`，其中有 `manifest.json` 和 `run/`。这些目录保存在本地。没有原始文件时，可从各节链接的实测记录查到输入、轮次和已验证范围。[构建与产物核对](debugging-and-collaboration.md) · [真机操作与恢复](device-test-playbook.md#6-故障定位与恢复)

## 1. 选一个动作，写出完成条件

先选影响日常使用、当前能区分原因的一项。将「桌面卡」具体到「从设置上滑回主屏，手指移动期间画面停住」，将「搜索异常」具体到「搜索进程退出，从崩溃报告所列词典读取同一区间返回 EIO」。未知项写「待测」，注明准备从哪份记录或哪个入口取得。

```text
用户动作和预期结果：
最近一次失败的版本、输入、环境和实际结果：
本轮打算改变的一个条件：
通过时用户会看到什么，用哪份输出复核，原先可用的哪项功能需要复测：
```

失败样本和正常样本使用相同输入，沿输入、处理、交付到显示或读回逐层比较。先找最后相同和最早不同的位置。跨进程用事务、帧号或呈现时间戳配对，缺少标识的相邻日志只能说明发生在同一时段。例如，应用在黑窗出现前已经交付正确画面，下一步查合成和显示。如果首帧直到黑窗消失才交付，查应用启动与首次绘制。

## 2. 核实基线，分配并行工作

先读三个仓库的实际状态。顶层只记录子模块提交，子模块内未提交的代码和新文件要分别查看。

```sh
git status --short --branch
git submodule status
git -C hackios-xnu-kernel status --short --branch
git -C hackios-xnu-userland status --short --branch
```

- 负责实现的人记录基线提交、可修改的文件、生产入口及测试输入。另一项改动已占用同一构建目录时，在独立目录使用相同基线构建。替换共享库、内核或分析器前先与使用者核对。正在比较的两轮沿用同一版分析器。
- 负责设备的人串行执行真机命令。同一次开机可以依次验收几个正常入口，比较两版时每轮只更换一个影响结果的条件。其他成员可并行复算日志、编译和跑主机回归。设备成员返回轮次名、实际动作、动作前后状态及原始文件位置。
- 打包后从两份 `manifest.json` 核对 `kernel.sha256`、`pack.driver_sha256`、`pack.air_sha256`、`pack.jobs_effective` 与启动参数。查看 `pack.worktree_status`，将其他成员的改动与实际构建输入逐项核对。怀疑库或文件漏装时，从最终镜像读回目标文件，检查内容、属主和父目录的访问权限。[载荷构成与上机核对](k90auto-run-protocol.md#2-载荷记录这一轮跑的是什么)
- 新一批测量前先读完上一批。K90 每批最多三轮。结束后退出相机等高耗能应用，检查桌面、系统进程和 GPU 状态。复盘后选择下一个变量，确认需要人体感知的项目及需观察的现象。[真机轮运行规则](k90auto-run-protocol.md)

## 3. 对照异常画面与同一次操作的日志

记录入口、显示内容、外观设置，以及异常出现在首次打开、转场还是停稳后。取同一界面的正常图和异常图，先直接查看原图，再对工具标出的区域做像素比较。`good_shot` 和 `test_shot` 是两张同尺寸截图的路径。`visual-audit.py` 需要 NumPy、Pillow，可读取 1156×2510 的 BGRA 原始截图或 PNG。

```sh
python3 tools/k90auto/visual-audit.py "$test_shot" --baseline "$good_shot"
python3 tools/k90auto/render-health.py "$round" --baseline "$baseline" --examples 1
```

第一条命令报告黑块、顶栏或底栏可疑区域的坐标。同屏原本为黑色的内容也可能命中。其退出码为零时仍应查看每张图的检查结果。第二条按进程及错误类型列出快照中出现的日志，先读覆盖时段与合并缺口，再查异常画面附近新增的管线拒绝、进程重启或 GPU 错误。日志按次数限流的项目仅能确认出现过。

短暂黑窗需要前后连续画面。旧版「提醒事项」录像中，第 448、449、450 个采样依次为模糊桌面、黑色窗口、列表，采样率仅 10 Hz。另一次冷开同一应用，104 幅扫描输出均与显示时间线匹配，未复现。两次记录分别支持「采到过一幅黑窗」与「本次冷开未复现」，黑窗持续的刷新次数及成因仍未知。[打开应用时的黑色窗口](../progress/2026-11-21-user-test-issues.md#10-打开应用时的黑色窗口u13)

视频或相机图像先检查呈现时间戳、尺寸、平面、行距和颜色范围。逐字节比较只取有效像素。格式有量化时，记录差异像素数、最大误差和单位。核对视频时分别统计回调状态、非空图像和唯一呈现时间戳。一次 H.264 测试收到 270 次回调，其中两次报告丢帧且图像为空。用系统 AVPlayer 正常播放同一文件，按呈现时间戳与独立解码参考比较，270 帧的有效 NV12 字节散列全部匹配。[H.264 逐帧对照](../analysis/2026-11-11-multimedia-validation.md#9010-首包-finish-的逐帧回归)

## 4. 从桌面手势找到耗时的那一帧

对保存了 `touch_lat=1` 的轮次先核实快照的合并与覆盖，再计算手势期间的帧间隔。以下最后一条的 `120` 为示例轮次的 `fb_hz`，其他轮次取本轮实际值。

```sh
round=docs/progress/evidence/k90auto/kernel-12377-s21-prdt1-cilookup1
python3 tools/k90auto/summary.py --verify "$round"
python3 tools/k90auto/gestures.py --each "$round"
python3 tools/k90auto/hitch.py "$round" --top 2
python3 tools/k90auto/frame-split.py "$round" 120
```

1. 查看 `summary.py` 的 `coverage`，对照动作时段和日志最大缺口。合并校验通过表示现有快照中的记录已正确合并，所有快照同时缺失的时间仍可能覆盖一次手势。
2. `gestures.py` 按按下位置给手势分类，用拷贝完成时刻统计。`--each` 另列每次控制中心下拉。其帧间隔分布排除了至少 90 ms 的空档。上滑回主屏等动作需对照当轮操作顺序确认。查拖动中停顿时，读 `hitch.py` 的面板计数、最长间隔和对应 swap。
3. `frame-split.py` 分列面板锁存观测与旧日志的拷贝起点。选中长间隔后，在相邻 swap 的 `tl: s`、`tl: v`、`tl: l` 中核对提交、拷贝和锁存观测的实际时间。脚本的 G 段是根据提交和 ready 估算的区间，逐笔 GPU 执行耗时须有该笔的硬件起止记录。
4. 查 CPU 绘制，用同一线程的 Core Animation 起止事件、期间的 swap ID 和驱动的 `SwapEnd` 入口配对。一次回主屏采到 7 拍间隔，驱动在下一帧开始拷贝后才读到上一次锁存。按原始时序核对，下一帧 2234 从 CA 开始到 `SwapEnd` 为 59.043 ms，面板拷贝及提交为 4.428 ms。该轮缺少 GPU 硬件起止记录。CPU 编码与 GPU 执行可以重叠，两者需要分别计时。[手势分项与长间隔](../analysis/2026-11-22-global-review.md#33-手势分项与长间隔)

同一输入、同一采集选项下分别报告墙钟、线程 CPU 时间之和及用户动作结果。首次、预热和复开分组，保留温度、负载和影响工作量的设置。前摄曾在八段并行出图对照中缩短出图墙钟，却增加线程 CPU 消耗。同一暗场从系统相机复测，两版均约 15 帧/秒，开发分支保留原实现。[前摄预览的处理器开销](../analysis/2026-11-22-global-review.md#43-预览的处理器开销)

## 5. 从普通入口验收基本功能

先确定调用方能读取什么、预期内容来自哪里。主机测试应运行生产代码，故障条件放在可丢弃的输入或模型中。真机用原来的正常入口、相同输入及独立参考结果复核。

| 用户现象 | 如何区分出错环节 | 如何验收 |
|---|---|---|
| 搜索进程反复退出 | 从崩溃报告取文件名、错误码和偏移。将同一区间经普通文件读取、原卷同步读取及主机参考文件分别比较。主机运行 `python3 tools/run-host-tests.py ufs-prdt`，检查偏移和缓冲类型改变后读写结果及两侧字节 | 修复轮以 4 KiB 为单位读完 14,906,940 字节的词典，核对全文件 SHA-256，再确认同轮的进程 PID 和最新崩溃报告时间。[词典读取验收](../analysis/2026-11-24-sysdic-ufs-dma-corruption.md#4-验收范围) |
| 录音文件存在但听不到声音 | 分别从 AVAudioRecorder 和原始麦克风入口录制，检查样本数、峰值和是否全零。用已知频率的外放音调，比较播放前和播放中录到的该频率能量 | 原轮 `record_test 5` 取得 240000 个样本。另一次 `micloop_test 6 raw tone 2` 的 1000 Hz 分量随扬声器播放上升 89.5 dB。两次检查分别覆盖应用录音输出和物理声音采集。[真机录音结果](../progress/2026-11-24-mic-m8-resolved.md#3-真机录音结果) |

## 6. 按验证结果交接和提交

| 结果 | 处理 |
|---|---|
| 原动作未复现或日志未覆盖 | 标明版本、输入、动作次数与已覆盖时间，保留最近一次有效失败样本。下一轮补缺失的时段或字段。 |
| 只有局部指标改善 | 保留局部读数，复测普通应用、原场景和相邻功能。用户动作耗时持平且 CPU 消耗增加时，记录撤回候选的理由。 |
| 同一输入能随改动重现、消除故障 | 核对两版实际运行的产物，补相邻场景回归。若一次替换多处，逐项撤回以确定必要改动。 |
| 需要实物、人工或外部输入 | 写出已验证范围、缺少的条件、需要人做的一个动作和预期观察，转做可独立验证的工作。 |

整合人亲自核对变更、构建输入、原始日志和回归结果。对每个涉及的仓库查看 `git diff`、`git diff --cached` 和未跟踪文件。子模块实现与测试在所属仓库提交，顶层用 `git diff --submodule=log` 核对子模块指针范围。已暂存的指针用 `git diff --cached --submodule=log`。技术结论只在所属专题展开，顶层指针与结论一同更新。提交前在顶层执行 `python3 tools/check-docs.py`。

同一故障的排查、实现与复测形成一个阶段。每次测量的读数与未验收候选留在工作树或本地忽略目录。阶段已有可复核的修复、排除结论或独立验收结果，并能说明适用范围，再提交相应代码、测试和文档。原始截图与日志留在本地，提交前逐仓审阅暂存内容和隐私信息。[提交与隐私约定](../../AGENTS.md)

交接时填明接手者可以直接复查的内容。

```text
用户动作与验收条件：
已验证的正常版本和实际运行产物：
仍失败的具体输入、条件与结果：
已试过且不值得原样重复的方案，以及原因：
下一项动作、可区分的两种结果、各自对应的下一步：
改动归属、恢复方法、本地原始资料位置、干净克隆可读的替代来源：
```
