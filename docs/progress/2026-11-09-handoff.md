## 3. 架构审查各项的处理

- 已落地：§3.3 架构总览，§17 启动参数目录与钩子清单，§16 合入前检查。
- 已实测：§7.1 的缓存跨开机。上机构建的 Mesa 一直关闭 ir3 磁盘缓存；打开后第一次开机正常写入，第二次开机解锁后约 1.5 分钟内全黑（开机较慢的可能没有排除），改回关闭，`setup-mesa-arm64e.py` 同步改为关闭，见 [ir3 磁盘缓存跨开机实测](../analysis/2026-11-09-ir3-disk-cache.md)。按 11-06 以后的脚本从干净克隆构建的 Release 需要核对这一项。
- 已落地：§13 的崩溃报告。`mkjobs.py --rest` 去掉了按需任务的 XPC activity 登记，写报告的 `osanalyticshelper` 以 CHECK_IN 登记时取不到 criteria，在 OSASubmissionClient 触发 XPC API Misuse 后反复退出。保留这部分登记并登记 `osanalyticshelper` 后，报告写进 `systemgroup.com.apple.osanalytics/DiagnosticReports/`，跨开机保留，每个进程到 25 份为止，见[用户态崩溃报告](../analysis/2026-11-09-crash-reports.md)。
- 已核对：§13 的页大小推断。真机 `hw.pagesize` 与 `vm.pagesize` 都是 16384，与 iOS 用户态的 16 KiB 页一致。
- 已删除：`libannibale-fpvolume.dylib`（内核已对 `/private/var` 报告 apfs）与 `inject.c` 的 `personasAreSupported` 钩子（iOS 26 镜像不注入 containermanagerd）。默认镜像不再把 `libannibale.dylib` 注入 backboardd：它的窗口服务器与亮度钩子按 iOS 16.5 地址校验，在 23G90 上不安装，只留 `TOUCH_LAT=1` 时的诊断用途，见[注入钩子清单 §3](../analysis/2026-11-09-injection-hooks.md#3-结论)。
- 已删除：钩子清单里 `MGCopyAnswer` 的磁盘容量部分。MobileGestalt 自己从 disk0 的 `kIOMediaSizeKey` 取到 128 GB，「关于本机」显示总容量 128 GB、可用 109.99 GB，见[注入钩子清单 §3](../analysis/2026-11-09-injection-hooks.md#3-结论)。
- 试做未合入：§16 的注入库自报 UUID。各库在构造函数里经 `kern.annibale.say` 打印 LC_UUID，开机后较晚启动的进程（MercuryPosterExtension、nsurlsessiond、日历）留下了这一行，SpringBoard、backboardd、iconservicesagent 已加载库却没有，原因未查，改动已撤回。
- 未处理：§21 列出的待用户决定事项、P0 的脏区重绘与材质样本、11-06 清单拆分、Metal 驱动自报 UUID。钩子清单里标为「待评估」的各项需要逐项改到对应层。

## 4. 遗留问题

- nearbyd、cloudd、MessagesBlastDoorService、airplayd 开机后反复崩溃，初步归类见[用户态崩溃报告 §5](../analysis/2026-11-09-crash-reports.md#5-遗留)；报告在 `DiagnosticReports/` 下，`rwq ipsframes` 读触发线程的调用栈，地址减去当次开机的 shared cache slide（内核 `userabort` 行打印）后再查符号。
- IPA 管理器的开机登记不稳定。它靠 `com.annibale.appinst`（`RunAtLoad`，在 `user/501` 域执行 `appinst register-system`）在开机时登记进 LaunchServices：
  - 放行 osanalytics 的验证镜像那次开机，这个任务运行 42 秒后以 `exit(1)` 退出，当次输出不在日志窗口里。
  - `beb26cce…` 与当前 `boot_a`（`8cdb013b…`）开机后，`rwq apps` 里都没有 `com.annibale.installer`；开机完成后以 root 或 mobile 手动执行一次 `appinst register-system` 都立即成功，图标回到第二页。
  - 当前 `boot_a` 的 `appinst` 只在已有记录指向别的路径时才注销，这次开机前记录同样已经不在，所以丢失发生在 LaunchServices 一侧，与 `appinst` 先注销无关。
  - 同一镜像不换 `boot_a` 直接重启一次（08:16），开机后记录又不在；开机时的 `appinst register-system` 运行 90 秒后打印「LaunchServices refused system app com.annibale.installer」并 `exit(1)`，开机完成后再执行立即成功。`com.annibale.appinst.plist` 的注释说 LaunchServices 按卷与文件 ID 记录 bundle，换根盘镜像时记录失效；这次没有换镜像也失效，`/annibale` 在每次开机挂载的 ramdisk 上，文件 ID 是否每次都变还没有核实。
  - CoreServices 里有「Database was seeding; client will retry and block. This is not an error.」和「LSDatabaseBuilder: posting LSNotificationDatabaseSeedingComplete for UID %u」：建库期间客户端的登记请求会阻塞，与这 90 秒相符。换回 `8cdb013b…` 后 08:23 那次开机，这个任务运行 67 秒后 `exit(0)`，IPA 管理器在第二页，所以开机登记时成时败，被拒时都等了 90 秒以上。08:20 试过给 `com.annibale.appinst` 加 `com.apple.notifyd.matching` 的 `com.apple.LaunchServices.DatabaseSeedingComplete` 并保留 `RunAtLoad`：开机时那次照样 96 秒后被拒，之后任务没有再被拉起，没有登记上，改动已撤回。下一步确认这个通知是否经 notifyd 发出，或任务在运行中收到事件时 launchd 是否丢掉它，再决定触发方式。
- 开机时系统在后台拉起的已安装应用（本轮为 Kumone），点图标后不切到前台；结束这个进程后再点可以正常打开。
- 主屏图标出现得晚，几次开机表现不同：
  - 上一版镜像第一次开机后约 3 分钟，部分图标画出，其余是空白占位。
  - 同一镜像第二次开机后约 6 分钟内，iconservicesagent 占用约一个处理器，主屏图标、Dock 和日历组件全部透明。它空闲后翻页仍不显示，锁屏再解锁后几乎全部画出，只剩日历图标空白和天气组件黑底。
  - 第二次开机解锁后图标立即出现，按这一点看图标图像在锁屏前已经生成，主屏没有刷新的原因待查；与之前记录的图标缓存问题是否同一原因也没有核实。
  - 当前 `boot_a` 开机后约 4 分钟，从「设置」回到主屏时图标、Dock 与日历动态图标全部画出，天气与日历组件仍是黑底。
- 仍以 annibale 命名、实际只服务 POCO X5 Pro 的代码：`annibale_wifi.c`、`annibale_wlfw.c` 与 ath11k 路径（WCN6750），`annibale_adreno.c`（Adreno 642L），`annibale_guard.c`。这批代码与 K90 的 ath12k、A830 路径共用部分文件，删除前要逐个确认调用方。
